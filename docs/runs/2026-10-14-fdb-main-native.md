## 决策日志（问题 / 默认 / 理由 / 回滚 / 外审）

1. **不等 PR 合入就开录。** 默认今天下午开录。理由：录音与 ASR 占 GPU，统一评分离线可重算，提前一天给后面的轮次制、级联和服务指标留余量。回滚：评分口径变了只需离线重算；录音有问题就在下一租约重录。外审：未做（排期决定，不涉及口径）。
2. **重录而不是复用 10-09/10-10 的录音。** 默认重录。理由：主表要出自同一个代码版本，且 10-09 的导出清单是旧格式，`unified-score` 不接受。回滚：若时间不够，用当前导出器重导旧录音。外审：未做。
3. **每张卡一路会话，分 8 片。** 同卡并发会改变被测延迟，所以每卡一路。租约已是 8 卡，释放重申 4 卡会清空节点上已装好的环境，因此改为 MiniCPM-o 分 8 片：GPU 时长与 4 卡相同，墙钟减半。代价是 GPU 利用率低于 80%，测量有效性优先；服务层的并发表另行扫描。回滚：无。外审：未做。
4. **节点环境。** 镜像自带 sglang 0.5.19，main 钉 0.5.21（缺 `SpawnRanks`），在容器内按 main 的 `pyproject.toml` 执行 `pip install -e .`；上传的源码缺 `.git`，runbook 记录服务端版本要用 `git rev-parse HEAD`，因此从公开仓库按同一提交拉一层元数据，工作区与上传内容一致。

### 用客户端口径重算（10-15 14:20 PT，离线，未用 GPU）

服务指标只能用客户端在协议上看到的东西来算，任何讲同一套协议的服务端才能横向比（Jeffro 的 sglang-omni#2843，分支 `fdb-infra-metrics` 的 `f269b707`）。上表依赖 sglang-omni 自带的服务端事件记录（#2544），换别的服务端就没有。为确认换口径不丢信息，用 #2843 的 `benchmark_duplex_serving report` 对上面同一份录音重算，结果 `docs/runs/fdb-main-20261014/minicpmo-serving-2843.json`。

| 并发 | 单元延迟 p50 / p90 / p99 (ms) | 超时单元 | 首包音频 p50 / p90 (ms) | 所需起播缓冲 p50 / p90 (ms) | 80 ms 缓冲下卡顿的回复 |
| --- | --- | --- | --- | --- | --- |
| 1 | 180 / 208 / 271 | 0/432 | 187 / 205 | 52 / 96 | 9/39 |
| 2 | 206 / 263 / 402 | 0/432 | 218 / 272 | 49 / 99 | 8/36 |
| 4 | 211 / 320 / 474 | 0/432 | 235 / 421 | 56 / 119 | 15/39 |
| 8 | 282 / 416 / 604 | 0/432 | 282 / 562 | 114 / 251 | 21/35 |

- 对账：两种口径数到的单元相同（每档 432 个），客户端单元延迟的中位数比服务端的就绪到完成多 1 到 2 ms，最大值相差约 1 ms（并发 1：654 对 653 ms）。服务端记录对主表指标没有额外信息，只多出各阶段拆分，属于诊断用途。
- 读法：MiniCPM-o 的回复音频按 1 秒单元随输入产出，回复的实时率（RTF）p50 约 0.99，由输入节奏决定，不反映服务快慢，所以 native 的达标线用超时单元率而不是 RTF。卡顿那一列说明客户端要留的缓冲随并发增大：并发 8 时 p90 要约 250 ms，80 ms 不够。
- 决定：sglang-omni#2834（服务端口径的 runbook 步骤）由 #2843 取代，建议关闭；它多出的只有 runbook 里自动起服务这一层便利。
